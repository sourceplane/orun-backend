## 2. Create The Migration Harness

Implement a small, production-leaning Postgres migration harness in
`packages/db/src/`.

At minimum it should provide:

- a migration metadata type
- migration file discovery or an explicit migration manifest
- deterministic ordering by version/filename
- validation that migration filenames are unique and monotonic
- an `orun_schema_migrations` table contract
- an `applyMigrations` flow that:
  - creates the schema migrations table if needed
  - reads already-applied migrations
  - applies pending migrations in order
  - records checksum/name/applied timestamp
  - runs each migration in a transaction where appropriate
- a status/list function that reports applied vs pending
- clear errors for checksum mismatch or duplicate migration identity

The harness should be testable without a live database by using a narrow client
interface or fake client. If you add a CLI/script that uses `DATABASE_URL`, it
must fail closed with a clear message when `DATABASE_URL` is absent and must not
print the URL.

Suggested scripts are acceptable but not mandatory if equivalent package
commands exist:

```bash
pnpm --filter @orun/db migrate
pnpm --filter @orun/db migrate:status
pnpm --filter @orun/db migrate:check
```

Do not require a live Supabase project for default unit tests.

## 3. Add First Core Schema Migration

Create the first V2 Postgres migration under `packages/db/migrations/`, for
example:

```text
0001_core.sql
```

This migration should implement the bounded first core schema from
`spec/v2/01-data-model.md`:

- `users`
- `user_identities`
- `organizations`
- `organization_members`
- `organization_invites`
- `billing_accounts`
- `entitlements`
- `projects`

Include the relevant constraints and indexes from the V2 data model:

- UUID primary keys using Postgres/Supabase-compatible UUID defaults
- tenant-owned rows carry `organization_id`
- project-owned rows carry `project_id` where applicable
- role/status/lifecycle/provisioning check constraints
- unique organization slug
- unique organization/project slug
- unique provider identity
- tenant-scoped indexes that start with `organization_id`
- invite email lookup index on `lower(email)`
- timestamps and soft-delete fields where specified

Use plain SQL that is appropriate for Supabase Postgres. If you enable an
extension for UUID generation, do it idempotently. If you add updated-at
triggers/functions, keep them generic and tested by SQL/text checks.

Do not include catalog, run/job/step, GitHub installation, repository, policy,
audit, or usage tables unless you find a strong dependency in the specs. Those
are better as follow-up migrations once the harness exists.

Do not add RLS policies unless the spec gives enough detail to implement them
safely. It is acceptable to document that RLS policies are deferred to the V2
auth/authorization task.

## 4. Add Typed Boundaries Without Fake Behavior

Export useful types and helpers from `@orun/db` for future V2 work:

- migration types/helpers
- core domain row/input types for the tables created in `0001_core.sql`
- ID/slug validation helpers if useful

Avoid fake store methods that pretend to read/write a database but return
hardcoded data. If you add service/store modules, they must either be real and
tested against the migration client abstraction, or be limited to types and
interfaces that later tasks can implement.

The Worker must not import `@orun/db` in this task unless it is purely a
type-only compile check with no runtime behavior change.

## 5. Tests And Validation

Add focused tests in `packages/db` that prove:

- migration filenames are parsed and sorted deterministically
- duplicate or out-of-order migration identities fail clearly
- migration checksums are stable
- `applyMigrations` applies pending migrations once and records them
- already-applied migrations are skipped
- checksum mismatches fail before applying new migrations
- `0001_core.sql` contains the required tables, indexes, constraints, and
  tenant-scoped columns
- no migration contains obvious secret placeholders such as database URLs,
  access tokens, API keys, or private keys

If a live Postgres/Supabase smoke is easy and credentials are available, you may
run it against a disposable/local database. Do not make live access required for
PASS. Record clearly whether live migration smoke was run.

# Required Outcomes

## 1. Make `@orun/db` Safe For Worker Use

Before wiring the Worker to `@orun/db`, split or expose package entrypoints so
Worker runtime imports do not pull in Node-only modules.

Required shape:

- keep CLI/migration execution working with `pg`, `node:fs`, and `node:crypto`
- provide a Worker-safe export path for:
  - `DbClient` and query result types
  - row/input domain types
  - ID/slug helpers
  - onboarding stores/services added by this task
- avoid importing `NodePgClient`, migration loader, or Node filesystem/crypto
  code into `apps/worker`
- update tests so `apps/worker` build/typecheck catches accidental Node-only
  imports

Acceptable implementations include:

- `@orun/db/runtime` or `@orun/db/worker` for Worker-safe code
- `@orun/db/node` for `NodePgClient`, loader, CLI, and migration-only helpers
- preserving the root export if it remains compatible with existing CLI/tests,
  as long as Worker imports use the safe subpath

Do not enable broad Node compatibility in the Worker just to paper over a bad
package boundary.

## 2. Add Typed Core DB Stores/Services

Add focused store/service modules under `packages/db/src/` for this first V2
slice. Keep SQL out of Worker handlers.

Required behavior:

- upsert or ensure a user profile by Supabase/Orun user ID
- upsert or ensure GitHub identity when provider identity claims are present
- list organizations for a user through active `organization_members`
- create an organization transactionally:
  - validate slug and name
  - insert `organizations`
  - insert owner `organization_members` row for the caller
  - insert `billing_accounts` placeholder
  - insert default entitlement rows if useful for limits/onboarding
  - return a typed organization summary
- get organization detail only when caller has active membership
- create project under an organization:
  - require permission
  - validate slug/name/description
  - enforce `(organization_id, slug)` uniqueness through DB errors or explicit
    lookup
  - return typed project summary
- list/get projects visible in an organization, excluding deleted rows

Add unit tests for the stores/services using a narrow fake `DbClient` or a
disposable Postgres path where the repo already supports it.

## 4. Add V2 Auth Context And Authorization Helpers

Add V2 auth/context code without breaking V1 `authenticate()`.

Required behavior:

- represent `RequestContextV2` from `spec/v2/02-auth-and-authorization.md`
- support dashboard-user auth for V2 routes through Supabase JWT verification
  when Supabase auth env vars are configured
- keep the issuer, audience, and JWKS URL configurable; do not hardcode the
  project URL or secret values
- sync the user and GitHub identity lazily during `/v2/me` or authenticated V2
  dashboard requests
- support existing Orun CLI/session tokens for V2 read routes only when the
  token includes enough stable user identity to resolve Postgres membership
- add role/permission helpers such as:
  - `requireOrgPermission(ctx, orgId, "org.view")`
  - `requireOrgPermission(ctx, orgId, "project.create")`
  - `requireProjectPermission(ctx, orgId, projectId, "project.view")`
- role mapping must match the minimum V2 permission table:
  - owner/admin/member/viewer
  - owner/admin/member can create projects
  - viewer can view org/project/catalog/run but cannot create projects
- handlers must call authorization helpers before tenant-owned DB access

Test Supabase JWT verification with local/generated JWKS fixtures or extracted
generic JWKS utilities. Do not require live Supabase auth for unit tests.

## 6. Add V2 API Routes

Add the first V2 route group to `apps/worker/src/router.ts` and focused handler
modules.

Implement:

```text
GET  /v2/me
POST /v2/organizations
GET  /v2/organizations
GET  /v2/organizations/:orgId
POST /v2/organizations/:orgId/projects
GET  /v2/organizations/:orgId/projects
GET  /v2/organizations/:orgId/projects/:projectId
```

Response shapes should be typed in `@orun/types` or a clearly named shared V2
contract module.

Required route behavior:

- `GET /v2/me` returns the current user and organization memberships with
  permissions
- `POST /v2/organizations` accepts `{ name, slug }` and returns `201`
- `GET /v2/organizations` returns only organizations visible to the caller
- `GET /v2/organizations/:orgId` requires `org.view`
- `POST /v2/organizations/:orgId/projects` requires `project.create`
- `GET /v2/organizations/:orgId/projects` requires `org.view`
- `GET /v2/organizations/:orgId/projects/:projectId` requires `project.view`
- invalid UUIDs/slugs/bodies return the existing JSON error envelope
- duplicate org/project slugs return `CONFLICT`
- unauthenticated requests return `UNAUTHORIZED`
- authenticated but unauthorized requests return `FORBIDDEN`

Keep the API responses compact and stable. Do not leak internal SQL errors.

# Current Repo Context

Local remote-state is still not equivalent to GitHub Actions remote-state.

The user hit this local command failure from `sourceplane/orun`:

```text
./orun run --remote-state -i examples/intent.yaml

Error: initializing remote run: init run: create run: Session creates require namespaceId (code: INVALID_REQUEST)
```

Why this happens:

- GitHub Actions remote-state gets namespace identity from OIDC claims.
- Local remote-state uses an Orun CLI session token, which currently authenticates the human but does not automatically resolve the current GitHub repo to a namespace ID for `POST /v1/runs`.
- The CLI can only send `namespaceId` if `orun cloud link` has already persisted repo linkage in `~/.orun/config.yaml`.
- Existing `orun cloud link` cannot create/resolve a new backend repo link unless the repo was already linked through dashboard flow.

# Objective

Add a session-authenticated backend API that lets a local Orun CLI session resolve and link the current GitHub repo to a namespace ID without sending or storing a GitHub PAT or GitHub OAuth access token in the CLI.

After this task, the backend must expose enough information for `sourceplane/orun` to make local `orun run --remote-state` behave like GitHub Actions remote-state: repo identity is resolved automatically from the authenticated context and current Git remote, then the CLI can create the remote run with `namespaceId`.

# Required Outcomes

## 1. Store Namespace Slugs During CLI Auth

The backend already discovers admin repo IDs during OAuth/device login to create `allowedNamespaceIds`.

Change the auth implementation so it also preserves repo slug mappings:

- Fetch admin repos as `{ namespaceId, namespaceSlug }`, not IDs only.
- Upsert every visible admin repo into the `namespaces` table during CLI and dashboard auth.
- Keep session claims as IDs only if that is the existing token contract.
- Do not store GitHub access tokens.
- Do not return GitHub access tokens to the CLI.

This is required because later repo resolution needs to map `sourceplane/orun` to the GitHub repo ID.

If an older session token predates this change and the namespace slug is not in D1 yet, return a clear typed error from the new endpoint that tells the CLI/user to run `orun auth login` again.

## 2. Add Session Repo Link/Resolve Endpoint

Add a new endpoint:

```text
POST /v1/accounts/repos/link
Authorization: Bearer <orun-cli-session-token>
Content-Type: application/json

{ "repoFullName": "owner/repo" }

200/201 -> {
  "namespaceId": "...",
  "namespaceSlug": "owner/repo",
  "linkedAt": "..."
}
```

Behavior:

- Require session auth.
- Require `sessionKind="cli"` for this no-GitHub-token path.
- Validate `repoFullName` with the existing owner/repo validation rules.
- Resolve `repoFullName` against rows in `namespaces`.
- Require the resolved namespace ID to be present in the CLI session's `allowedNamespaceIds`.
- Create or reuse the `accounts` row for the GitHub login.
- Create or reuse the `account_repos` link.
- Return the linked namespace.

Failure behavior:

- Missing/invalid body: `INVALID_REQUEST`.
- Non-CLI session: `FORBIDDEN`.
- Repo slug not known in D1: typed `NOT_FOUND` with guidance that the user may need to re-login after the backend update.
- Repo slug known but not in `allowedNamespaceIds`: `FORBIDDEN`.
- Do not leak internal D1 details.

Keep the existing `POST /v1/accounts/repos` route with `X-GitHub-Access-Token` intact for dashboard/admin flows.

Be explicit:

- GitHub Actions uses OIDC namespace claims.
- Local CLI uses Orun CLI session token plus current Git remote slug.
- The backend resolves the slug to a namespace ID from session-discovered namespace slugs.
- The CLI should not hold or forward GitHub OAuth tokens.

## 5. Tests

Add or update tests for:

- OAuth login upserts namespace slug mappings.
- Device login upserts namespace slug mappings.
- `POST /v1/accounts/repos/link` succeeds for a CLI session whose allowed namespace IDs include the repo ID.
- The endpoint is idempotent.
- The endpoint rejects dashboard sessions.
- The endpoint rejects unknown repo slugs with a useful typed error.
- The endpoint rejects known repo slugs outside `allowedNamespaceIds`.
- Existing `POST /v1/accounts/repos` with `X-GitHub-Access-Token` still works.
- `POST /v1/runs` still requires `namespaceId` for sessions and accepts it after the account link exists.

# Constraints

- Do not store GitHub OAuth access tokens or GitHub PATs.
- Do not return GitHub OAuth access tokens to the CLI.
- Do not broaden dashboard sessions so they can mutate remote-state routes.
- Do not remove the existing dashboard/admin repo linking route.
- Avoid a migration unless the existing `namespaces` and `account_repos` tables are insufficient.
- Keep responses typed and consistent with the existing error envelope.
- If you discover the proposed endpoint cannot be implemented safely with existing auth scopes, write a proposal under `ai/proposals/` and stop before weakening security.

# Objective

Implement the Cloudflare Queue consumer code path for catalog ingestion.

The consumer must read `CatalogIngestMessage` batches from
`CATALOG_INGEST_QUEUE`, load the raw catalog envelope from R2, defensively
validate it, normalize component/relation/event rows into the routed catalog
index, and rely on Queue retry behavior for transient failures.

# Required Outcomes

1. Add a Worker queue handler.
   - Add `async queue(batch, env, ctx)` to `apps/worker/src/index.ts`.
   - Delegate to a small testable function, for example
     `handleCatalogIngestQueue(batch, env, ctx)`.
   - Keep `fetch` and `scheduled` behavior unchanged.

2. Make catalog normalization reusable.
   - Extract the current private validation/normalization helpers from
     `apps/worker/src/handlers/catalog.ts` into a small shared module, or export
     them cleanly from a module that is not route-specific.
   - Both `POST /v1/catalog/sync` fallback and the queue consumer must use the
     same normalizer logic.
   - Avoid duplicating component validation, status derivation, relation ID
     derivation, or event logic.

3. Process queue messages safely.
   - Accept only `CatalogIngestMessage`-shaped messages.
   - Read the raw envelope from R2 using `message.envelopeRef`.
   - Re-run envelope validation defensively:
     - supported schema version
     - source repo ID and repo slug match the message
     - source commit matches the message
     - components is an array
     - component IDs, names, and paths are valid
   - Route the write through `makeStorageRouter(env).catalogForNamespace`.
   - Normalize components, relations, and events into the routed catalog index.
   - Do not write raw envelopes, plans, logs, component states, JWTs, or tokens
     into D1 or logs.

4. Handle retries intentionally.
   - For malformed messages or invalid envelopes, acknowledge/drop the message
     after logging only safe metadata. Do not retry poison messages forever.
   - For transient R2/D1/normalization failures, let the message retry by
     throwing from the queue handler or marking the message for retry.
   - Prefer per-message handling so one poison message does not force unrelated
     valid messages in the same batch to retry forever.
   - Follow current Cloudflare Queues APIs for `MessageBatch`, message `ack`,
     and message `retry`.

5. Preserve current deployment safety.
   - Do not add `DB_CATALOG_0` / `DB_CATALOG_1` to `wrangler.jsonc`.
   - Do not activate multi-shard D1.
   - If you add a queue producer/consumer binding to `wrangler.jsonc`, keep it
     disabled from production unless the required Cloudflare resource and
     migration behavior are documented and tested. A code-only consumer is
     acceptable for this task.
   - Do not introduce Postgres/Hyperdrive.

6. Tests.
   - Unit/integration tests for queue consumer success:
     - receives `CatalogIngestMessage`
     - reads envelope from R2
     - calls shared normalization
     - writes component state refs/rows in single-DB fallback
   - Tests for invalid/poison messages:
     - missing required message fields
     - missing R2 object
     - invalid envelope JSON
     - source repo ID/repo/commit mismatch
     - bad component path
   - Tests for retry behavior:
     - transient D1/R2 failure is retried or thrown
     - poison message is acked/dropped without retry
   - Existing catalog sync/read tests must still pass.

# Integration Notes

- Cloudflare module Workers support a `queue(batch, env, ctx)` handler for Queue
  consumers. The `MessageBatch` includes messages and supports ack/retry behavior
  through normal return/throw plus explicit message methods.
- The current `CatalogQueue` type is intentionally small for the producer. You
  may need to add queue consumer message/batch types in `packages/types` or use
  Cloudflare worker global types directly in `apps/worker`.
- `R2Storage` may need a helper to read an object by exact key/ref and parse JSON.
  Prefer a typed helper over ad hoc R2 access scattered in the consumer.
- If a poison message is acked/dropped, log only: upload ID, namespace ID, repo
  ID, and safe error code.
- If delivery wiring changes, run local kiox/orun validation per the verifier
  protocol.

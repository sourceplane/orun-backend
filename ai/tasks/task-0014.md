# Required Outcomes

## 1. Authenticated Product Shell

Replace the current top-only run shell with an authenticated app shell:

- Left navigation: Catalog, Runs, Repositories, Settings.
- Top bar: Orun product mark, current GitHub login, account/repo scope signal, global search or contextual search, refresh, and sign out.
- Catalog must be the default authenticated view.
- Keep OAuth login, callback parsing, fragment cleanup, session storage, account creation, and sign out working.
- Show typed API errors with retry affordances where a retry is useful.
- Handle token-expired or unauthorized API responses by showing a clear sign-in-again path rather than a broken table.

The shell may use a small in-app route/state machine. Once component detail exists, make Catalog and Component Detail URL-addressable with either lightweight browser history or hash routes. Do not add a router framework for this slice.

## 2. Catalog Home

Add a catalog home view backed by `client.listCatalogComponents`.

Required capabilities:

- All Components table as the default view.
- Table/card segmented view toggle.
- Filters for:
  - repo
  - owner
  - type
  - status
  - free-text query
- Use backend query parameters where available instead of filtering everything only in memory.
- Component rows/cards show:
  - component name and title
  - type
  - repo slug
  - owner/team
  - system/domain
  - lifecycle
  - environments
  - latest status
  - latest plan checksum when present
  - last seen timestamp
  - tags
- Empty states for:
  - no linked repos
  - linked repos but no synced components
  - filtered search with no matches
  - failed catalog load
- Long component IDs, repo names, paths, tags, and checksums must not break layout on desktop or mobile.

Do not hard-code production mock catalog data. Test fixtures are fine.

## 3. Component Detail

Add a component detail view backed by the catalog detail APIs.

Required fields and sections:

- Overview:
  - name/title
  - type
  - repo
  - path
  - owner
  - system
  - lifecycle
  - tags
  - environments
  - latest plan checksum
  - latest commit
  - current status
  - first seen and last synced timestamps
  - current state R2 ref as a copyable/displayed artifact reference
- Dependencies:
  - outgoing dependencies from `getCatalogComponentDependencies`
  - incoming dependents from `getCatalogComponentDependencies`
  - empty states for both directions
- Recent runs:
  - use `getCatalogComponentRuns`
  - show status, repo, trigger, actor, job counts, created time
  - allow selecting a run to open the existing run detail/log view
- History:
  - use `getCatalogComponentHistory`
  - show event type, commit, PR number when present, upload ID, created time
  - this can be a compact first-slice table/list

The component detail can use tabs or stacked sections. Keep it work-focused and scannable.

## 4. Runs View Preservation

Keep the existing operational Runs workflow intact:

- Recent runs table with repo namespace, status, trigger, actor, job counts, and timestamps.
- Search/filter by repo, status, or run ID at minimum.
- Run detail with metadata, jobs grouped by component, and log viewer.
- Existing log loading, 404 no-log handling, and grouped job behavior must continue to work.

It is acceptable and encouraged to move runs code into `apps/dashboard/src/features/runs/*` while preserving behavior.

## 5. Repositories View

Add a Repositories view backed by `client.listLinkedRepos` plus catalog component data.

Required fields:

- repo slug / namespace slug
- namespace ID
- linked timestamp
- component count derived from catalog rows
- last catalog sync derived from the max component `lastSeenAt` for that repo
- latest component status summary where available
- state for linked repo with no synced catalog data yet

Do not add browser repo-link creation. Do not ask the user for GitHub PATs or GitHub access tokens. The dashboard remains read-oriented for repo data in this task.

## 6. Settings View

Add a light Settings view:

- signed-in GitHub login
- API base URL
- allowed namespace count or linked repo count
- sign out action
- note whether an account has been created

Do not add mutable execution controls or arbitrary action dispatch.

## 7. Feature Structure

Split the dashboard enough to keep it maintainable. Suggested structure:

```text
apps/dashboard/src/App.tsx
apps/dashboard/src/features/catalog/*
apps/dashboard/src/features/runs/*
apps/dashboard/src/features/repos/*
apps/dashboard/src/components/*
```

This is a guideline, not a required exact tree. Keep modules small, typed, and testable.

# Frontend Design Constraints

- Build the actual authenticated catalog product surface, not a landing page.
- Keep the UI quiet, dense, and operational. Avoid oversized hero copy, decorative cards, ornamental gradients, and marketing-style layouts.
- Do not put cards inside cards. Use cards only for repeated items, compact detail panels, or modals.
- Use compact tables, tabs, segmented controls, filters, and status chips.
- Keep cards at `8px` radius or less.
- Do not introduce a large UI framework, global state framework, charting library, or router framework.
- Do not use a one-note palette. The current app is dark and compact; improve contrast and scanability without turning the whole UI into one hue family.
- Make desktop and mobile layouts stable. No overlapping text, no buttons whose labels overflow, and no table columns that make the page unusable on narrow screens.
- Use accessible buttons, inputs, labels, focus states, and table/list semantics. Icon-only buttons need labels or tooltips.

# Constraints

# Integration Notes

- The catalog list API returns `CatalogComponentListResponse` with `components` and `total`.
- `CatalogComponentSummary.repoId` is the GitHub numeric repo ID. `repoFullName` is the user-facing slug.
- `CatalogComponentDetail.currentStateRef` is an R2 object reference, not necessarily a browser-downloadable URL. Display it as an artifact reference unless the backend exposes a safe read URL.
- `getCatalogComponentRuns` currently resolves runs by component name, so results are best-effort.
- `getCatalogComponentDependencies` may return empty relations for a nonexistent component in some edge cases noted by Task 0013 verifier. Component detail should still fetch the component first and treat a missing component as not found.
- Repository sync health must be derived from linked repos plus catalog rows for now; there is no dedicated sync-health endpoint yet.
- The app is deployed by `cloudflare-pages-turbo`; dashboard file changes should produce a changed component in `orun plan --changed`.

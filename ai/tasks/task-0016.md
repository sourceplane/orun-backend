The accepted architecture update from `scalable-db-conversations.txt` keeps the
project Cloudflare-first but rejects the long-term "one giant D1" shape. The
target is core D1 for lean control-plane metadata, D1 catalog/run shards for
queryable derived indexes, R2 for raw artifacts/logs/envelopes/snapshots, Queues
for async ingestion pointer messages, Durable Objects for live coordination, and
Hyperdrive/Postgres only as a later escape hatch.

# Objective

Introduce the storage routing seam and first scalable catalog ingestion path
without a broad product rewrite.

The implementation should preserve the current single-`DB` local/bootstrap
behavior while making catalog/run index access route through an explicit storage
router. Add queue-backed catalog ingestion where a queue binding is available,
with the existing `ctx.waitUntil` normalizer retained as the fallback.

# Required Outcomes

1. Add a typed storage router seam.
   - It must distinguish core D1 from catalog/run index D1.
   - It must preserve `env.DB` as the default single-D1 fallback.
   - It must centralize shard selection so handlers do not choose shard bindings
     directly.
   - It should be small and boring: deterministic hash routing is enough.

2. Add bounded catalog shard support.
   - Introduce a config shape that can map shard names/bindings without assuming
     one D1 binding per tenant.
   - Start with a small shard count suitable for tests/local dev.
   - Ensure dashboard reads across multiple visible namespaces group work by
     routed shard instead of scanning every shard.
   - Keep compatibility with the current single-DB migration state.

3. Route catalog sync and catalog reads through the storage router.
   - `POST /v1/catalog/sync` should use the routed catalog index.
   - catalog list/detail/history/runs/dependencies endpoints should query only
     shards that correspond to visible namespaces.
   - local namespaces must remain excluded from global catalog reads.

4. Add queue-backed catalog ingestion.
   - Add an optional `CATALOG_INGEST_QUEUE` binding/type path.
   - After OIDC validation and R2 persistence, enqueue a pointer message when the
     binding exists.
   - Queue messages must contain namespace/repo/upload IDs, commit SHA,
     timestamps, and R2 refs only. They must not contain full envelopes,
     component states, plans, logs, or tokens.
   - Preserve the current `ctx.waitUntil` normalization path when no queue
     binding is configured.
   - Share validation/normalization code between queued and fallback paths where
     practical.

5. Update docs/specs only where needed to reflect implementation details.
   - Do not rewrite the architecture docs broadly; this task already has updated
     specs.
   - If implementation reveals a behavior, contract, security, persistence, or
     deployment change beyond these specs, write a proposal under
     `ai/proposals/task-0016-spec-update.md`.

# Constraints

- Do not make D1 authoritative for live execution state. Durable Objects remain
  the source of truth for job claims, dependencies, heartbeats, and run state.
- Do not store raw catalog envelopes, full plans, component states, logs, or
  large snapshots in D1.
- Do not add one D1 binding per tenant as the first scale step.
- Do not introduce Postgres/Hyperdrive in this task; leave the seam compatible
  with that future backend.
- Do not break the current deployed single-D1 shape.
- Keep Worker handlers thin. Routing decisions belong in a small router/helper,
  not scattered across endpoint code.
- Keep queue handling testable without live Cloudflare credentials.
- Do not print or persist GitHub tokens, Orun refresh tokens, JWTs, raw
  envelopes, or large component payloads in logs.
- Respect existing namespace boundaries and dashboard read authorization.

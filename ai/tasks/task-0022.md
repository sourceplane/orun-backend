# Current Repo Context

Tasks 0001 through 0021 are complete. Task 0021 created and verified the V2
database package:

- `packages/db` exists as workspace package `@orun/db`
- `packages/db/migrations/0001_core.sql` contains the bounded 8-table V2 core
  schema
- migration harness exports `applyMigrations`, `getMigrationStatus`,
  `loadMigrations`, and `checksumSql`
- `NodePgClient` and CLI scripts exist for live Postgres execution
- local/unit checks pass, but the verifier could not run a live database smoke
  because Docker/local Postgres was unavailable

The user wants database provisioning brought earlier so new DB work can be
tested as it is developed. This task is therefore promoted ahead of Supabase JWT
verification and `/v2` API work.

V2 specs require Supabase/Postgres to become the primary relational system of
record, with Supabase project/database resources provisioned through
Tactonic/Terraform and application DDL owned by `packages/db`. Existing V1
Cloudflare/D1/R2/Durable Object/Queue behavior must remain live and compatible.

Current repo reality:

- no `infra/`, `terraform/`, or Supabase provisioning tree exists yet
- `.orun/compositions.lock.yaml` currently lists generic `terraform` but not an
  obvious first-class `supabase-postgres` composition export
- `spec/v2/07-provisioning-and-operations.md` defines the target
  `orun_supabase_database` / `supabase-postgres` contract
- GitHub Actions must use `SUPABASE_API_KEY` as the canonical Supabase
  Management API secret name

# Objective

Add the earliest safe V2 database provisioning and smoke-test path:

- introduce repo-local Tactonic/Terraform scaffolding for Supabase/Postgres
  provisioning using the V2 contract
- add a CI/local Postgres migration smoke so `@orun/db` migrations are executed
  against a real Postgres database on PRs
- add an on-demand, plan-first GitHub Actions workflow for Supabase/Tactonic
  provisioning that can later apply to dev/preview/staging with explicit
  approval/inputs
- run or document live Supabase provisioning only when credentials/account/region
  are clear

The goal is to let every future DB/schema task prove its migrations against real
Postgres immediately, while keeping shared Supabase provisioning safe,
idempotent, and non-destructive.

## 3. Add A Real Postgres Migration Smoke For Development

Future DB work must be testable before shared Supabase provisioning is fully
settled. Add a PR-safe smoke path that runs `@orun/db` migrations against a real
Postgres instance without requiring Supabase credentials.

Preferred shape:

- a GitHub Actions workflow or job using a disposable Postgres service container
- a package script or small verification script that:
  - runs `pnpm --filter @orun/db migrate`
  - verifies `orun_schema_migrations` contains `0001_core.sql`
  - verifies all 8 core tables exist
  - verifies at least one expected index or constraint exists
  - does not print `DATABASE_URL`

This smoke should run on PRs when `packages/db/**`, `infra/supabase/**`, or the
workflow itself changes. It can also be callable by `workflow_dispatch`.

If adding a separate workflow, name it clearly, for example:

```text
.github/workflows/v2-db-smoke.yml
```

If integrating into the existing Orun-driven CI is cleaner, do that instead,
but do not make unrelated Worker/dashboard deploy jobs require database secrets.

## 4. Add Plan-First Supabase Provisioning Workflow

Add an on-demand GitHub Actions workflow for Supabase/Tactonic provisioning, for
example:

```text
.github/workflows/v2-db-provision.yml
```

The workflow should support at least:

- `workflow_dispatch`
- environment input such as `dev`, `preview`, `staging`, `prod`
- mode input such as `plan` or `apply`, defaulting to `plan`
- explicit branch/ref input if useful for safe testing

Safety requirements:

- `plan` must run before any `apply`.
- `apply` must require explicit input and should respect GitHub environment
  protections for staging/prod.
- The workflow must fail closed or skip with a clear message when
  `SUPABASE_API_KEY` is unavailable.
- It must not print secrets, connection strings, provider tokens, database URLs,
  JWTs, or Terraform sensitive outputs.
- It must upload only sanitized plan summaries/artifacts.
- It must not destroy or replace existing V1 Cloudflare Worker/D1/R2/Queue
  resources.

For this task, it is acceptable for production apply to be documented/blocked
until environment protections and account targeting are verified.

## 5. Run Migrations Against A Provisioned Or Disposable Database

After provisioning or local Postgres setup, run the real migration command:

```bash
pnpm --filter @orun/db migrate
```

Then verify against the database:

- `orun_schema_migrations` exists
- migration version/name/filename/checksum for `0001_core.sql` is recorded
- all 8 core tables exist:
  - `users`
  - `user_identities`
  - `organizations`
  - `organization_members`
  - `organization_invites`
  - `billing_accounts`
  - `entitlements`
  - `projects`
- at least one expected index exists, such as `idx_projects_org`
- at least one expected constraint exists, such as a role/status/lifecycle check

If Supabase credentials/account/region are unavailable, run the disposable local
Postgres smoke in CI/local instead and state clearly that shared Supabase apply
was not run.

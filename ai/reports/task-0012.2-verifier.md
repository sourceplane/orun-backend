## Security Review

**FAIL — Security-Sensitive Spec Drift in Commit `61f2ba8`**

Task 0012.2 specification (`ai/tasks/task-0012.2.md:118`) requires:

> "Requires the resolved namespace ID to be in `allowedNamespaceIds` from the session token."

`spec/04-worker-api.md:96` states:

> "Requires the resolved namespace ID to be in `allowedNamespaceIds` from the session token."

The implementation in `handleLinkRepoFromSession` after commit `61f2ba8`:

```typescript
// accounts.ts:374-417
export async function handleLinkRepoFromSession(rc: RouteContext): Promise<Response> {
  if (rc.authCtx.type !== "session") throw new OrunError("FORBIDDEN", ...);
  if (rc.authCtx.sessionKind !== "cli") throw new OrunError("FORBIDDEN", ...);
  // validates repoFullName...
  const ns = await lookupNamespaceBySlug(rc.env.DB, rawRepoFullName);
  if (!ns) throw new OrunError("NOT_FOUND", ...);
  // ← NO CHECK against allowedNamespaceIds
  const account = await getOrCreateAccount(rc.env.DB, rc.authCtx.actor);
  const link = await linkRepo(rc.env.DB, account.account_id, ns.namespace_id, ...);
  return json({ namespaceId: link.namespace_id, ... });
}
```

The accounts.test.ts test at line 870-879 explicitly confirms this behavior:

```typescript
it("succeeds for a known slug not in allowedNamespaceIds (stale session)", async () => {
  dbState._namespaces["other-ns"] = { namespace_id: "other-ns", namespace_slug: "other/repo", ... };
  const resp = await routeRequest(
    req("POST", "/v1/accounts/repos/link", { repoFullName: "other/repo" }),
    env, ctx,
  );
  expect(resp.status).toBe(200);  // passes even though "other-ns" is not in allowedNamespaceIds
});
```

**Authorization impact**: Any authenticated CLI user can call `POST /v1/accounts/repos/link` with any `repoFullName` that exists in D1 (placed there by any other user who authed with admin access to that repo). This creates an `account_repos` row. Because `resolveSessionNamespaceIds` (`accounts.ts:159-180`) unions JWT `allowedNamespaceIds` with D1 `account_repos` rows, the linking user can now pass that `namespaceId` in `POST /v1/runs`. This means any authenticated CLI user may create remote-state runs attributed to a namespace they do not own or control.

**The PASS criteria from the verifier task are not met:**

1. The check does not exist elsewhere — `resolveSessionNamespaceIds` provides a compensating control at run-creation time, but that is orthogonal to the link endpoint authorization.
2. No accepted proposal exists in `ai/proposals/` relaxing this requirement.
3. The check has not been restored.

**The spec (`spec/04-worker-api.md`) is inconsistent with the implementation and has not been updated.**

## Issues

1. **[BLOCKER — Security]** `handleLinkRepoFromSession` does not check that the resolved namespace ID is in `allowedNamespaceIds`. Any authenticated CLI user can link any known repo slug to their account, gaining run-creation access to that namespace via `resolveSessionNamespaceIds`.
   - File: `apps/worker/src/handlers/accounts.ts`, function `handleLinkRepoFromSession`
   - Spec reference: `spec/04-worker-api.md:96`, `ai/tasks/task-0012.2.md:118`
   - Test confirming behavior: `apps/worker/src/handlers/accounts.test.ts:870-879`

2. **[MINOR]** `spec/04-worker-api.md:96` is inconsistent with the current implementation and has not been updated to reflect the relaxed behavior.

## Risk Notes

- The `cli` session-kind gate is in place and functioning — dashboard sessions cannot call this endpoint. The scope of exposure is limited to authenticated CLI sessions.
- However, CLI session creation requires only a valid GitHub account (any account, not necessarily one with access to the target repo). The only gate on which repos end up in D1 is whether _any_ user logged in with admin access to those repos.
- `resolveSessionNamespaceIds` at `POST /v1/runs` does not add an additional ownership check beyond "account_repos row exists for this account+namespace." A user who links a foreign namespace can create runs under it.
- If remote-state is logically isolated per account (not just per namespace), the practical impact may be lower than described. But this isolation is not visible in the current code review scope and the spec contract is clear.

## Spec Proposals

A remediation proposal should be written at `ai/proposals/task-0012.2-link-auth-model.md` that either:

**Option A (Restore check):** Restore the `allowedNamespaceIds` check in `handleLinkRepoFromSession`. Sessions with stale claims must re-login to get an updated JWT. Provide a clear re-login error. Update spec to match.

**Option B (Accept relaxed model with compensating controls):** Explicitly document that any CLI session may link any known repo slug (because `lookupNamespaceBySlug` succeeds only for repos already registered in D1 via another user's auth), with compensating controls: (a) `linkRepo` creates an `account_repos` row scoped to the linking account; (b) run isolation must be confirmed per-account; (c) spec/04-worker-api.md must be updated; (d) the rationale (stale-session UX improvement) must be documented.

If Option B is accepted, update the test name from "succeeds for a known slug not in allowedNamespaceIds (stale session)" to something that clearly communicates the intended security model.

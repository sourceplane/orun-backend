## Security Findings

All principal security invariants verified. No failures found.

### Invariant 1 — CLI session without `githubUserId` fails closed

`handleLinkRepoFromSession` (`accounts.ts:459-464`) checks `rc.authCtx.githubUserId` and throws `FORBIDDEN` with re-login guidance if absent. Same guard in `resolveNamespaceForMutableAccess` in `jobs.ts` and `logs.ts`. Old sessions without the claim cannot progress on any mutable or link route.

### Invariant 2 — Link endpoint uses account-scoped cache, never global namespace table

`handleLinkRepoFromSession` (`accounts.ts:486-494`) calls `lookupRepoInAccountCache(rc.env.DB, account.account_id, rawRepoFullName)` — a query against `account_repo_cache WHERE account_id = ? AND repo_full_name = ?`. It does **not** call `lookupNamespaceBySlug` or query the global `namespaces` table. A globally-known repo slug absent from the caller's cache returns typed `NOT_FOUND`.

Pattern search confirmed `lookupNamespaceBySlug` does not appear in the CLI session link path.

### Invariant 3 — Local namespace IDs are server-derived and immutable

`deriveLocalNamespaceId` (`accounts.ts:443-445`) returns `local:user:${githubUserId}:repo:${repoId}` where both IDs come from signed JWT claims and the backend's own `account_repo_cache`. Clients cannot supply or override these values.

Prefix collision between users is structurally impossible: GitHub numeric user IDs contain no `:` character, so `local:user:111:repo:` cannot be a prefix of `local:user:1110:repo:` (the `:` after the user ID disambiguates).

### Invariant 4 — CLI session cannot create run under canonical repo namespace

`handleCreateRun` (`runs.ts:89-95`) immediately rejects any `namespaceId` not starting with `"local:"`:
```typescript
if (bodyNs && !bodyNs.startsWith("local:")) {
  throw new OrunError("FORBIDDEN", "Session tokens may not create runs under canonical repo namespaces...");
}
```
When the client provides `repoFullName`, the handler resolves via `lookupRepoInAccountCache` and derives the local namespace — canonical IDs are never considered.

### Invariant 5 — CLI session cannot reach another user's local namespace on mutable routes

`resolveNamespaceForMutableAccess` in both `jobs.ts:36-50` and `logs.ts:35-49`:
1. Requires `githubUserId` (fails closed otherwise)
2. Builds `localPrefix = "local:user:<githubUserId>:repo:"`
3. Filters `resolveSessionNamespaceIds` result to only namespaces starting with this prefix
4. Only then searches for the run

A session with GitHub user ID `11111` cannot find a run under `local:user:22222:repo:987654321`.

### Invariant 6 — Dashboard sessions cannot mutate

`assertMutableAccess` in both `jobs.ts:18-22` and `logs.ts:17-21` rejects any session that is not `sessionKind === "cli"` or `type === "oidc"`.

### Invariant 7 — OIDC tokens cannot write to local namespaces

OIDC namespace IDs come from verified GitHub Actions `repository_id` claims — always numeric strings. They cannot start with `"local:"`. The local prefix filter in `resolveNamespaceForMutableAccess` means no OIDC namespace can be resolved as a local namespace.

### Invariant 8 — Token refresh preserves `githubUserId`

`handleCliToken` (`auth.ts:168-169`) looks up the account by login, reads `github_user_id` from the account row, and conditionally includes it in the new access token. Sessions created before the migration will lack `github_user_id` in the DB, producing a token without the claim — which correctly fails closed.

### Minor finding (non-security, dead code)

`assertNamespaceAccess` (`runs.ts:19-34`) is exported but not called anywhere in the codebase. It uses the old `allowedNamespaceIds.includes(namespaceId)` pattern for session types, which would not correctly check local namespace IDs against the JWT's canonical repo IDs. Since this function is dead code, it poses no security risk. The actual mutable-route handlers use inline prefix-based logic that correctly enforces the local namespace boundary. Recommend removing or rewriting `assertNamespaceAccess` to reflect the new model in a follow-up.

## Residual Risk

1. **No authenticated live smoke**: Positive path (CLI token → `namespaceKind: "local"` response) was not exercised live. Security properties are fully verified in code; live positive smoke is deferred to task-0012.3 end-to-end testing.
2. **Dead code `assertNamespaceAccess`**: The exported function in `runs.ts` uses the old `allowedNamespaceIds` check and would produce incorrect results if called with a local namespace ID. It is currently unreachable but should be removed or rewritten before it can be re-introduced accidentally.
3. **`handleCreateRun` does not call `linkRepo`**: If a CLI session calls `POST /v1/runs` with `repoFullName` without first calling `POST /v1/accounts/repos/link`, the local namespace will not appear in `account_repos`. Subsequent claim/update calls by the same session would fail NOT_FOUND because `resolveSessionNamespaceIds` would not return the namespace. This is a functionality concern (not a security concern) and is addressed by the intended CLI flow: `orun cloud link` precedes `orun run --remote-state`.
4. **Migration applied at Cloudflare deploy time**: D1 migration `0004_local_namespaces.sql` was applied as part of the CI deploy job. Schema correctness was not verified with Wrangler D1 introspection; verification of the live schema is deferred. The migration uses safe `ALTER TABLE ... ADD COLUMN` and `CREATE TABLE IF NOT EXISTS`-equivalent patterns that preserve existing data.

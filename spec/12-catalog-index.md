# Spec 12 - Catalog Index and Sync

## Scope

This spec defines the cloud data layer that turns Orun plans, component descriptors, run history, and GitHub workflow context into a queryable dashboard catalog.

The Orun Dashboard product direction is a Git-native software catalog plus CI intelligence layer. The dashboard must not become the source of truth for components. Git remains authoritative; Orun Cloud stores the index, history, graph, raw artifacts, and automation records needed to render the product.

The catalog index supports `spec/11-dashboard-ui.md`.

---

## Product Model

The system has four layers:

```text
Source of truth     Git repos, component descriptors, intent.yaml, stack.yaml
Compile layer       orun plan / validate / changed-component detection
Cloud index         normalized catalog, run history, PR history, relations
Product UI          catalog, component pages, dependency graph, insights
```

Every Git commit may produce a catalog event. Every Orun plan may produce a graph event. Every run produces an execution event. The dashboard materializes these events into a searchable catalog.

## Data Concepts

### `component.json`

Source-owned descriptor, committed with the component. The exact source-side filename can evolve, but the normalized shape must support:

```json
{
  "apiVersion": "orun.io/v1",
  "kind": "Component",
  "metadata": {
    "name": "api-edge-worker",
    "title": "API Edge Worker",
    "description": "Cloudflare Worker that serves the public API edge.",
    "tags": ["cloudflare", "edge", "api"],
    "owner": "team-platform",
    "system": "saas-platform"
  },
  "spec": {
    "type": "cloudflare-worker",
    "lifecycle": "production",
    "repoPath": "apps/api-edge-worker",
    "environments": ["dev", "staging", "production"],
    "dependsOn": ["component:auth-worker"],
    "providesApis": ["api:public-edge-api"],
    "resources": ["resource:cloudflare-zone"]
  }
}
```

### `ComponentState`

Generated by `orun catalog export` from a plan and repo snapshot. It is an immutable observation for one component at one commit.

Required normalized fields:

```typescript
interface ComponentState {
  apiVersion: "orun.io/v1";
  kind: "ComponentState";
  source: {
    provider: "github";
    repository: string;      // owner/repo
    repoId: string;          // GitHub numeric repository ID
    branch?: string;
    commit: string;
    workflowRunId?: string;
    workflowRef?: string;
    prNumber?: number;
  };
  component: {
    id: string;              // stable within repo, e.g. github:<repoId>:<name>
    name: string;
    title?: string;
    description?: string;
    type: string;
    owner?: string;
    system?: string;
    lifecycle?: string;
    tags: string[];
    path: string;
  };
  environments: Array<{
    name: string;
    status?: "healthy" | "failing" | "stale" | "unknown";
    latestJobId?: string;
  }>;
  relations: Array<{
    relationType: "depends_on" | "provides_api" | "consumes_api" | "uses_resource" | "deploys_with";
    targetKind: "component" | "api" | "resource" | "composition" | "job";
    targetRef: string;
    environment?: string;
    jobId?: string;
  }>;
  plan?: {
    planId?: string;
    checksum: string;
    changed: boolean;
    affectedJobs: string[];
  };
  pr?: {
    number: number;
    title?: string;
    changedFiles: string[];
  };
  generatedAt: string;
}
```

### `CatalogSyncEnvelope`

Uploaded to Orun Cloud by GitHub Actions after `orun plan` and `orun catalog export`.

```typescript
interface CatalogSyncEnvelope {
  apiVersion: "orun.io/v1";
  kind: "CatalogSyncEnvelope";
  uploadId: string;
  schemaVersion: string;
  source: {
    provider: "github";
    repo: string;
    repoId: string;
    commit: string;
    branch?: string;
    workflowRunId?: string;
    workflowRef?: string;
    prNumber?: number;
  };
  plan?: {
    id?: string;
    checksum: string;
    objectRef?: string;
  };
  components: ComponentState[];
  generatedAt: string;
}
```

The first backend task should accept inline component states in `components`. A later task may support R2 object refs for large envelopes.

## Upload Flow

Recommended user workflow in GitHub Actions:

```text
orun validate
orun plan --changed --output plan.json
orun catalog export --plan plan.json --output catalog-sync.json
orun cloud sync --file catalog-sync.json --oidc
```

Backend flow:

1. Verify GitHub Actions OIDC.
2. Validate the envelope shape, size, schema version, repo ID, commit, component paths, and upload ID.
3. Store the raw envelope in R2 under the canonical repo namespace.
4. Normalize searchable records into D1.
5. Return `202 { uploadId, acceptedAt, componentCount }`.

The initial implementation may normalize synchronously or with `ctx.waitUntil`. Cloudflare Queues are a later scale step and must not be invented in config until a queue binding exists.

## API Endpoints

All catalog reads are dashboard session reads unless noted.

| Method | Path | Auth | Purpose |
|--------|------|------|---------|
| `POST` | `/v1/catalog/sync` | OIDC | Upload a signed catalog envelope for the calling repo namespace |
| `GET` | `/v1/catalog/components` | Session | List visible components across linked repo namespaces |
| `GET` | `/v1/catalog/components/:componentId` | Session | Get one component by ID if visible |
| `GET` | `/v1/catalog/components/:componentId/history` | Session | Get component catalog events and PR/change history |
| `GET` | `/v1/catalog/components/:componentId/runs` | Session | Get recent runs/jobs touching the component |
| `GET` | `/v1/catalog/components/:componentId/dependencies` | Session | Get outgoing and incoming component relations |
| `GET` | `/v1/repos/:repoId/components` | Session | List components for one linked repo namespace |

### `POST /v1/catalog/sync`

Request body: `CatalogSyncEnvelope`.

Authorization:

- Requires verified GitHub Actions OIDC.
- The OIDC `repository_id` claim must equal `envelope.source.repoId`.
- The OIDC `repository` claim must equal `envelope.source.repo`.
- Dashboard and CLI sessions cannot publish canonical catalog state.

Response:

```json
{
  "uploadId": "upl_01hx...",
  "acceptedAt": "2026-05-07T10:00:00.000Z",
  "componentCount": 3
}
```

### `GET /v1/catalog/components`

Query parameters:

| Parameter | Description |
|-----------|-------------|
| `q` | Text search over name, title, owner, system, repo slug, tags |
| `repoId` | Filter by canonical GitHub repo ID |
| `type` | Filter by component type |
| `owner` | Filter by owner/team |
| `system` | Filter by system/domain |
| `tag` | Filter by tag |
| `status` | Filter by derived health status |
| `limit` | Default 50, max 100 |
| `offset` | Default 0 |

Response:

```json
{
  "components": [],
  "total": 0
}
```

### Read Authorization

Dashboard catalog reads use the same linked namespace policy as run reads. A session can read catalog rows whose `namespace_id` is visible through the account's linked repo set. Local namespaces are not shown in the global catalog unless a later explicit "local runs" view is designed.

## Storage Model

D1 is the query index. R2 stores immutable raw artifacts. D1 must not store full catalog envelopes or large plan JSON blobs.

### R2 Layout

All keys start with the effective namespace ID to preserve the existing storage isolation rule:

```text
{namespaceId}/catalog/uploads/{uploadId}/catalog-sync-envelope.json
{namespaceId}/catalog/commits/{commitSha}/components/{componentName}.json
{namespaceId}/catalog/commits/{commitSha}/plan.json
{namespaceId}/catalog/prs/{number}/component-diff.json
```

### D1 Tables

Add a catalog migration after the current migrations:

```sql
CREATE TABLE catalog_uploads (
  upload_id       TEXT PRIMARY KEY,
  namespace_id    TEXT NOT NULL,
  repo_id         TEXT NOT NULL,
  repo_full_name  TEXT NOT NULL,
  commit_sha      TEXT NOT NULL,
  branch          TEXT,
  workflow_run_id TEXT,
  workflow_ref    TEXT,
  pr_number       INTEGER,
  envelope_ref    TEXT NOT NULL,
  component_count INTEGER NOT NULL,
  created_at      TEXT NOT NULL,
  FOREIGN KEY (namespace_id) REFERENCES namespaces(namespace_id)
);

CREATE TABLE catalog_components (
  component_id      TEXT PRIMARY KEY,
  namespace_id      TEXT NOT NULL,
  repo_id           TEXT NOT NULL,
  repo_full_name    TEXT NOT NULL,
  name              TEXT NOT NULL,
  title             TEXT,
  description       TEXT,
  type              TEXT NOT NULL,
  owner             TEXT,
  system            TEXT,
  lifecycle         TEXT,
  repo_path         TEXT NOT NULL,
  tags_json         TEXT NOT NULL,
  environments_json TEXT NOT NULL,
  latest_plan_id    TEXT,
  latest_plan_checksum TEXT,
  latest_commit_sha TEXT NOT NULL,
  latest_status     TEXT NOT NULL DEFAULT 'unknown',
  current_state_ref TEXT NOT NULL,
  first_seen_at     TEXT NOT NULL,
  last_seen_at      TEXT NOT NULL,
  FOREIGN KEY (namespace_id) REFERENCES namespaces(namespace_id)
);

CREATE TABLE catalog_component_relations (
  relation_id         TEXT PRIMARY KEY,
  source_component_id TEXT NOT NULL,
  relation_type       TEXT NOT NULL,
  target_kind         TEXT NOT NULL,
  target_ref          TEXT NOT NULL,
  environment         TEXT,
  job_id              TEXT,
  last_seen_at        TEXT NOT NULL,
  FOREIGN KEY (source_component_id) REFERENCES catalog_components(component_id)
);

CREATE TABLE catalog_component_events (
  event_id        TEXT PRIMARY KEY,
  component_id    TEXT NOT NULL,
  namespace_id    TEXT NOT NULL,
  upload_id       TEXT NOT NULL,
  event_type      TEXT NOT NULL,
  commit_sha      TEXT NOT NULL,
  pr_number       INTEGER,
  summary         TEXT,
  payload_ref     TEXT,
  created_at      TEXT NOT NULL,
  FOREIGN KEY (component_id) REFERENCES catalog_components(component_id),
  FOREIGN KEY (upload_id) REFERENCES catalog_uploads(upload_id)
);
```

`relation_id` must be deterministic from `(sourceComponentId, relationType, targetKind, targetRef, environment, jobId)` so relation upserts are idempotent.

Required indexes:

```sql
CREATE INDEX idx_catalog_components_namespace ON catalog_components(namespace_id, last_seen_at DESC);
CREATE INDEX idx_catalog_components_repo ON catalog_components(repo_id, name);
CREATE INDEX idx_catalog_components_owner ON catalog_components(owner);
CREATE INDEX idx_catalog_components_type ON catalog_components(type);
CREATE INDEX idx_catalog_events_component ON catalog_component_events(component_id, created_at DESC);
CREATE INDEX idx_catalog_relations_target ON catalog_component_relations(target_kind, target_ref);
```

## Normalization Rules

- Upsert the namespace as kind `repo` from OIDC claims.
- Upsert one `catalog_uploads` row per accepted envelope.
- Upsert `catalog_components` by `component.id`.
- Store tags and environments as JSON arrays in D1 for the first slice.
- Replace relation rows for each uploaded source component with the envelope's latest relation set.
- Add a `catalog_component_events` row when a component is first seen, when its latest commit changes, when its owner/type/system/lifecycle changes, or when PR metadata is present.
- Derive `latest_status` from environment statuses and latest run/job data when available; default to `unknown`.

The initial normalizer can be deliberately simple. It must be deterministic, idempotent by `uploadId`, and safe to replay.

---

## Security Requirements

- Catalog sync must not accept dashboard sessions or local CLI sessions for canonical repo catalog writes.
- OIDC repo claims must match the envelope repo fields exactly.
- Component paths must be relative paths inside the repository. Reject absolute paths, `..` traversal, and empty paths.
- Envelope body size must have a bounded limit. Start with 1 MiB unless implementation tests justify a different value.
- Unsupported `schemaVersion` values return `INVALID_REQUEST`.
- Duplicate `uploadId` returns the existing accepted response and must not create duplicate events.
- Do not log raw envelopes, JWTs, GitHub tokens, or large component payloads.

---

## Deferred Features

- GitHub App installation policy and repo allowlist.
- Queue-backed async normalization.
- R2 object refs for very large component states.
- PR diff ingestion from GitHub API.
- Scorecard calculation.
- Semantic search over docs/logs/runbooks.
- Approved dashboard actions and SaaS dispatch.

---

## Acceptance Criteria

- Shared types define catalog envelopes, component summaries, detail, relations, and event payloads.
- Worker exposes `POST /v1/catalog/sync` and the catalog read endpoints.
- Catalog sync stores raw envelopes in R2 and normalized rows in D1.
- Catalog read endpoints enforce linked repo visibility.
- Idempotent sync by `uploadId` is tested.
- OIDC repo mismatch and dashboard/session writes are rejected.
- Component path validation is tested.
- `@orun/client` includes typed catalog methods for the dashboard.
- Existing run/job/log endpoints remain behavior-compatible.

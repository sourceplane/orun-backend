

For **Orun SaaS**, I would **not use only D1 as the long-term primary database**.

Best strategy:

> **Cloudflare-first app + Postgres primary database + D1/DO/R2 where they fit.**

My recommendation:

```txt
Cloudflare Workers / Pages  → app/API/control plane
Supabase or Neon Postgres   → primary relational DB
Cloudflare Hyperdrive       → fast pooled DB access from Workers
Cloudflare R2               → logs, plan.json, catalog snapshots
Durable Objects             → live run coordination / locks / job state
D1                          → edge-local projections, cache, small control metadata
```

## Why not full D1?

D1 is much better now, especially with read replication. Cloudflare says D1 read replicas can lower latency and scale read throughput globally, and D1 supports point-in-time restore with Time Travel. But D1 still has important limits: Workers Paid allows **10 GB max per database**, **1 TB max storage per account**, and **1,000 queries per Worker invocation**. ([Cloudflare Docs][1])

That is fine for:

* small tenants
* config metadata
* lightweight catalog views
* edge projections
* public read-heavy pages

But Orun will eventually need:

* billing
* audit logs
* memberships
* invites
* RBAC/policy
* catalog history
* run/job history
* component snapshots
* usage metering
* analytics
* enterprise queries
* migrations
* reporting

That starts to look like a **serious relational control plane**, and Postgres is safer.

## Where D1 is excellent

Use D1 for:

```txt
tenant_edge_cache
latest_catalog_projection
project_summary_projection
read-heavy component indexes
small per-region lookup tables
public dashboard snapshots
```

D1 read replication is attractive for fast global reads, and Cloudflare says there are no D1 egress charges; read replication billing is based on rows read/written, not extra replica charges. ([Cloudflare Docs][2])

## Where Supabase/Postgres is better

Use Postgres for:

```txt
organizations
memberships
invites
projects
repositories
components
component_snapshots
runs
jobs
steps
billing_accounts
usage_events
audit_events
policies
permissions
integrations
```

Supabase gives you managed Postgres, Auth, storage, realtime, and easier SQL/relational ergonomics. Its Pro plan includes 8 GB database storage, 100K monthly active users, and then usage-based overages. ([Supabase][3])

For Orun, Postgres gives you:

* better joins
* stronger relational modeling
* mature migrations
* indexes
* JSONB
* full-text search
* analytics compatibility
* easier future migration to Neon/RDS/Cockroach
* better enterprise confidence

## Should you choose Supabase?

For MVP and first real SaaS: **yes, Supabase is a good choice**.

But I would use it mainly as:

> **Managed Postgres + Auth**, not as the whole platform.

Keep your app/control plane on Cloudflare.

Use:

```txt
Workers + Hyperdrive + Supabase Postgres
```

Cloudflare Hyperdrive supports connecting Workers to PostgreSQL-compatible databases and provides connection pooling/caching benefits for databases outside Cloudflare. ([Cloudflare Docs][4])

## Final recommendation

Use this staged strategy:

### Phase 1 — MVP

```txt
Cloudflare Workers
Supabase Postgres
Supabase Auth or Better Auth
R2 for plan/log/catalog blobs
```

### Phase 2 — Scale

```txt
Add Hyperdrive
Add Durable Objects for execution state
Add D1 for read projections
Add queue/event ingestion
```

### Phase 3 — Enterprise scale

```txt
Postgres primary
R2 immutable artifacts
ClickHouse/BigQuery for analytics
D1 edge cache/projections
DO for coordination
```

My strongest answer:

> **Do not build Orun’s main control plane fully on D1. Use Postgres as the source of truth. Use Cloudflare as the execution/control edge. Use D1 as a fast projection/cache layer, not the primary system of record.**

# Should you use per-tenant database?

For Orun: **not at the beginning**.

Use a **pooled multi-tenant database** first:

```txt
one Postgres database
many organizations
organization_id on every row
RLS/policy guards
```

This is the normal SaaS model for early and mid-stage products because it is cheaper, easier to operate, and much faster to evolve. AWS describes pooled tenancy as shared infrastructure used for efficiency and agility, while silo tenancy gives dedicated resources per tenant. Microsoft also notes that changing tenancy models later can be costly, so the choice should match scale, isolation, and operational needs. ([AWS Documentation][1])

---

# Best strategy: pool first, silo later for enterprise

Use this model:

```txt
Free / Pro / Team tenants
  → shared Postgres database

Enterprise tenants
  → optional dedicated database or dedicated schema later
```

This is called a **bridge model**: mix pooled and siloed isolation depending on tenant needs. AWS describes the bridge model as a hybrid approach that applies silo or pool where it makes sense. ([AWS Documentation][2])

For Orun, this is the best long-term model.

---

# Why not per-tenant DB from day one?

Per-tenant DB sounds clean, but it creates heavy operational burden:

```txt
tenant signup creates database
tenant migration must run N times
schema changes become harder
cross-tenant analytics harder
billing aggregation harder
support/debug harder
connection pooling harder
search harder
backup/restore automation required
```

It is good for:

* large enterprise tenants
* strict isolation
* compliance-heavy customers
* custom data residency
* dedicated SLAs

It is bad for:

* fast MVP
* many small users
* frequent schema evolution

AWS calls this the **silo model**, where tenants get dedicated resources such as separate databases. ([AWS Documentation][3])

---

# My recommendation for Orun

Start with:

```txt
Supabase/Neon Postgres as primary DB
organization_id everywhere
Postgres RLS for tenant isolation
R2 for large JSON/log blobs
Durable Objects for live run state
```

Later add:

```txt
enterprise_orgs.provisioning_mode = "dedicated_database"
```

Example:

```txt
Organization A → shared cluster
Organization B → shared cluster
Enterprise X  → dedicated Postgres database
Enterprise Y  → dedicated region/database
```

# Organization creation lifecycle

## 1. User signup

Create:

```txt
users
```

Then either:

* ask them to create org
* or auto-create org from name/email domain

```txt
Rahul's Organization
```

## 2. Organization creation

Create:

```txt
organizations
organization_members
billing_account
default_policy_set
audit_event
```

User becomes:

```txt
role = owner
```

## 3. Default project setup

Optionally create:

```txt
Default Project
```

But I prefer asking after GitHub connect.

Better:

```txt
Create org first
Connect GitHub
Select repo
Create project from repo
```

## 4. Invite members

Invite creates:

```txt
organization_invites
```

With:

* email
* role
* expiry
* token hash
* invited_by
* organization_id

When accepted:

* create user if needed
* create organization_member
* mark invite accepted

## 5. Workspace switching

After login, query memberships:

```sql
select organizations.*
from organizations
join organization_members on organization_members.organization_id = organizations.id
where organization_members.user_id = current_user_id;
```

UI shows:

```txt
Switch Organization
  Sourceplane
  Personal
  Acme Platform
```

# Final answer

Use:

```txt
Pooled Postgres multi-tenancy now
Bridge/silo model later for enterprise
```

Do **not** start with per-tenant databases.

Best Orun model:

```txt
Organization = tenant, billing, membership, security
Project = Git/repo/platform boundary
Component = catalog entity
Run = execution/plan history
Stack = platform realization model
```

This gives you speed now and a clean path to enterprise isolation later.
